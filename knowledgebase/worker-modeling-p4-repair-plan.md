## 3. R0：持久化执行记录、预算和工具锁

### 3.1 记录内容

在现有 task-owned `modeling-state` 内增加宿主独占写入的执行记录，不引入 controller 新状态或数据库协议。
每个调用先原子预留不可复用的 `callId`，写入 STARTED，再启动子进程，结束后写入结果。
记录至少包括：`assetId`、`requirementsHash`、`attemptId`、`callId`、阶段、路线、
开始/结束时间、退出码、超时/取消/停止确认、失败类型、输入/产物/图像/schema/prompt 哈希及证据路径。
原始响应和 stderr 保留；不记录凭据或完整环境变量。无法确认原因的错误标为 UNKNOWN，不能猜成质量 GAP。

将 `state.feedback` 作为最近一次修复反馈保留，同时持久化全部阶段结果；`failures: []` 不再承担执行历史的含义。
累计序号保存在状态中，不再依赖进程内 `sequence=0`；恢复时不删除或覆盖同名响应。
STARTED 无终态时先核验旧进程已停止；停止未确认则终止调度并保留现场，不启动竞争调用。
已预留的调用额度保守计入预算，即使崩溃点位于真正启动之前，也不通过恢复补回额度。

### 3.2 预算与恢复

- 作者尝试上限维持直接建模 3、复用 2、第三方清理 2；另外记录阶段调用数和真实质量修复数。
- 每次作者尝试的 blockout、宿主预览、final 继续共享默认 30 分钟；清理默认 5 分钟。
  这是单次尝试预算，不是整个任务预算；任务 `deadlineAt` 始终是更外层上限。
- 尝试开始时持久化 `startedAt`、`deadlineAt`、已消耗额度；恢复使用原截止时间。
  重启不能重新获得 30 分钟；blockout 已完成且哈希有效时，只继续尚未启动的下一阶段。
- 发生中断的作者阶段不能无记录地重放。确认进程停止后，失败阶段占用原尝试，后续按剩余尝试处理。
  已完成并封存的产物可以进入待验收状态，不必重新启动作者。
- 新状态使用执行协议版本 2，与资产合同版本 2 分开解释。旧活动状态继续由原版本处理，首批不做自动迁移。

扩充现有 `pinToolchain`，包含所有新增依赖、导入/渲染 helper、schema/prompt/rubric 哈希、
评审和作者策略版本、模型标识/推理配置、CLI/Blender/UE 版本及生效预算。仅保存非敏感配置。
现有工具锁已经包含部分 harness 和 validator 哈希；本批补全依赖闭包，不重新计算或改写旧批次的身份。
同一任务恢复时配置不一致应明确拒绝混用；新的工具策略需新任务或宿主明确创建的新修订。

**回归：** 在调用预留后、产物写入后、技术 PASS 后、视觉响应落盘后分别注入崩溃；验证记录不覆盖、额度不增加、
已完成阶段不重复执行。切换模型/策略/helper 后旧任务不能静默继续。取消和停止未确认不能触发重试或路线回退。

## 4. R1：统一 glTF 导入，消除辅助网格污染

在 `modeling_scene.py` 提供唯一的验收导入入口，glTF 导入设置 `disable_bone_shape=True`。
让资产验收、候选资源预览、场景查询与多视角渲染都使用它；清理 `modeling-asset-check.py` 的两处直接导入。
该选项由 [Blender 5.2 官方导入 API](https://docs.blender.org/api/5.2/bpy.ops.import_scene.html) 提供，
本机同一 GLB 的 A/B 已验证其效果；实施时再用安装版本运行回归。

不按对象名 Icosphere 或隐藏集合做宽泛过滤。真实导出网格即使隐藏、同名，也必须接受现有检查。
辅助物还可能污染边界尺寸、网格数量和相机取景，因此修复需覆盖共同导入入口，不能只屏蔽两个 gate。
递增 validator 版本，保留原技术、动作及视觉要求；读取资产时继续禁用自动执行脚本。

**回归：**

1. 对 rig-2/3 六个留存导出重新运行新检查器；原文件哈希保持不变，新报告单独保存。
2. 正例的材料、绑定、实际求值后顶点位移均通过；网格数量和视图不再包含导入辅助物。
3. 在临时副本中移除真实 Hand.R 材质/绑定、冻结要求的动作，分别触发对应 GAP。
4. 加入名为 Icosphere 的真实坏网格及隐藏坏网格，确保仍拒绝；静态 GLB 回归不退化。

这里只修复 DCC 导入误拒绝。rig-1 的超时/作者接口故障、最终视觉验收、UE skeletal 导入需各自验证，
不能由六份报告技术通过推导为角色任务已经通过。

## 5. R2：将评审故障与资产修复彻底分开

### 5.1 状态与错误处理

把 `author → validateAsset → 外层 catch 重试作者` 拆成持久化阶段：
`AUTHORING → TECHNICAL_PENDING → VISUAL_PENDING → ACCEPTED`。
技术 PASS 后保存源文件、导出、依赖、技术报告和全部图片的哈希快照；每次重评前核验。
真实 GAP 才进入下一次作者修复；新输出必须使用新目录、新产物哈希、新评审额度。
证据被改写属于完整性故障，不以重新渲染覆盖旧证据的方式继续验收。

| 结果类型 | 宿主动作 | 是否触发作者/路线变化 |
| --- | --- | --- |
| REVIEW_SCHEMA_INVALID / REVIEW_SERVICE_UNAVAILABLE / REVIEW_TIMEOUT | 在预算内对同一证据重评，记录原响应及具体错误 | 不增加作者尝试；不排除复用源 |
| TECHNICAL_RUNNER_ERROR | 对同一产物重跑检查器；有效技术 GAP 与进程故障分开 | 不直接修模型 |
| TECHNICAL_GAP / VISUAL_GAP | 将具体 gate/criterion 与证据传给作者，按原尝试上限修复 | 可以；复用预算耗尽且存在有效未解决 GAP 才标 `reuse_quality_gap` |
| AUTHOR_SERVICE_ERROR / AUTHOR_TIMEOUT / AUTHOR_SCRIPT_ERROR | 保留尝试与日志，按已有作者上限处理；可用源作为下一次输入 | 占执行尝试；不能伪装成视觉/技术 GAP |
| PROVIDER_UNAVAILABLE / PROVIDER_RESULT_UNUSABLE | 记录原因，直接进入 Blender 路线 | 必须回退；不重复创建付费任务 |
| CANCELED / STOP_UNCONFIRMED / INTEGRITY_ERROR | 停止后续调用，保留状态 | 不回退、不重试 |

最终评审耗尽后抛出带类型的 `VALIDATION_INFRASTRUCTURE_EXHAUSTED`，阻止建模循环和生产外层循环把它转成内容修复。
保留可诊断的待验收产物，不发布为 DCC_READY/ENGINE_READY，也不判为模型质量不合格。
使用现有宿主终止机制（包括 `hardFailure` 的循环控制语义），报告明确写“验收基础设施失败”，不能写“需求不可实现”。
耗尽后恢复仍受原额度限制；只有新的明确修订可以获得新预算。
作者尝试若全被服务/执行故障耗尽，同样保留对应故障类型，不能统一报“质量预算耗尽”或排除复用源。
评审故障与 Tripo 服务故障分开分类；后者继续满足原任务要求的自动回退规则。

### 5.2 明确重试预算

| 阶段 | 上限 | 耗尽处理 |
| --- | --- | --- |
| v2 需求 intake | 2 次，每次默认 120 秒 | 保留合同不可生成的失败；不能丢弃 v2 技术要求后继续 |
| 路线 evaluator | 2 次，每次默认 120 秒 | 记录 evaluator unavailable，保守选择 Blender；不标记候选资产质量不合格 |
| DCC / UE 最终视觉评审 | 每份冻结证据最多 3 次，每次默认 120 秒，总计最多 360 秒 | 验收基础设施失败；不启动作者或引擎集成返工 |
| 第三方 base 的视觉可用性评审 | 每份证据最多 3 次，同上 | 保留具体失败类型；结果无法验收时回退 Blender，不将其记为真实视觉 GAP |
| DCC / UE 技术检查进程 | 每份冻结产物最多 2 次，每次默认 300 秒，总计最多 600 秒 | 检查器基础设施失败；没有有效 gate 结果时不修模型 |

所有上限受任务截止时间约束，阶段截止时间和次数必须持久化。配置覆盖后的实际值写入工具锁；
重试退避也计入总时限。有效的 PASS 或 GAP 都立即结束本轮评审，不再次抽样争取不同结论。
非瞬时磁盘/权限/完整性错误直接报对应故障，不浪费完整重试预算。

当前 CLI 已传 `--output-schema`；修复重点是校验诊断与调度，而不是再加同一参数。
统一入口保存每次 schema/prompt/raw response；返回具体 JSON 路径、缺失字段、错误类型和原需求覆盖差异。
格式重试提示加入这些诊断及正确结构，但不自动改字段名、补 PASS 或把自然语言结论转换成合格响应。
同一执行器复用于 DCC、UE、路线及 base 评审，各自使用上表策略。
UE 只重评已有地图截图和技术报告；地图、uasset 或导出身份变化才重新验收，不能为格式错误重做导入。

**回归：** 格式失败两次后 PASS 时作者只执行一次；服务错误后成功亦然；三次格式失败不会进入下一作者尝试；
有效 GAP 才修复；恢复后评审额度和文件名不重复。复现第三改色样本的故障顺序，复用资产不被错误排除。
另外覆盖 UE 格式错误不触发生产返工、Tripo 无 key/无 credits/服务中断/下载坏文件回退、取消不回退、付费 ledger 不重复。

## 6. R3：通行空间进入合同，DCC 与 UE 使用同一规格

### 6.1 合同扩展

为新合同增加可选的 `traversal` 字段；旧 v2 合同可按原字节和哈希读取，不给历史合同偷偷补默认值。
扩展前后的 schema 能力写入工具锁。生成入口使用完整的 nullable 字段，存储/读取兼容 schema 允许旧合同缺省，
避免当前 `obj()` 自动把所有 properties 设为 required 而破坏兼容。
已有 `preservesContract` 继续严格禁止作者修订改变通行规格；新增通行目标需宿主创建新合同修订。

门洞基准拟采用以下明确规格；数值只用于该基准，不能强加给其他用户任务：

```json
{
  "traversal": {
    "version": 1,
    "space": "asset-local-meters",
    "capsule": { "radiusMeters": 0.42, "halfHeightMeters": 0.96, "axis": "Z" },
    "marginMeters": 0.005,
    "paths": [{ "id": "door-center", "startMeters": [0, -1, 0.97], "endMeters": [0, 1, 0.97] }],
    "ueQuery": { "channel": "Visibility", "traceComplex": false }
  }
}
```

坐标相对资产根节点，halfHeight 包括两端半球。检查正半径、halfHeight ≥ radius、有限坐标、非零路径和唯一 id。
已明确要求可通行但缺少体积/路径的任务返回 CONTRACT_INCOMPLETE；不得由作者临时猜尺寸。
没有要求通行的旧合同报告 NOT_REQUESTED，不宣称通过通行测试。通行字段存在时必须通过对应 gate。
首批只支持竖直胶囊体、直线路径、静态凸碰撞；弯曲路径可显式拆段，旋转胶囊/复杂动态通行暂不承诺。

### 6.2 DCC gate

读取 source 中经现有凸性/闭合校验的 UCX，统一变换到合同坐标。
计算整个胶囊体沿路径扫掠后与凸包的最小距离；不能用中心射线或稀疏位置采样替代体积检测。
实现有界的凸体距离算法：竖直胶囊体的扫掠体可表示为路径两端轴线端点的凸包加半径球，
以 support mapping / GJK 距离计算对每个 UCX 检查，最大迭代数 64；不收敛返回 GAP，不猜 PASS。
净空小于 margin 即拒绝，并记录 path、UCX、最小净空和算法状态。
这一检查适用于 source 碰撞；GLB 只含可视几何时，不能凭 GLB 证明 FBX 碰撞正确。

回归采用已知几何的独立期望值：敞开门框、完全封门、薄片横挡、起点重叠、偏心侧碰、边角临界、
仅略低于/高于净空阈值、对象缩放与旋转、非凸输入、算法未收敛。边界需覆盖数值容差，避免将过度保守近似误当精确通过。

### 6.3 UE gate

在实际测试地图中，用实际导入 StaticMeshComponent 的 simple collision 执行对应胶囊扫掠。
先验证导入源哈希、加载/编译就绪、component 可查询且阻挡选定通道；记录命中物、起点穿透与路径结果。
采用 margin 膨胀体积，与 DCC 的净空条件一致。
资产坐标到 UE 世界坐标必须基于导入轴变换、米转厘米及 component transform；不能靠排序尺寸推测轴向。
校准 90 度转向、位移及单位缩放；首批无法可靠处理的镜像/非均匀缩放明确拒绝。

保留既有 `engine-passage-*` 的正对照方式：在独立诊断场景/对象副本中放入必定阻挡的临时物体，
验证查询确实生效后销毁，不保存地图。目标资产验证仍只使用原场景；查询前后记录地图和资产文件哈希。
采用安装版本验证过的 HitResult 读取方法，不能把 API 异常或未就绪时的未命中计为通过。
API 语义参考 [Unreal SystemLibrary 胶囊查询文档](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/SystemLibrary?application_version=5.2)，
具体签名和行为以本机 UE 5.8.2 probe 为准。Visibility 通道通过仅证明该合同的查询，不等同于 CharacterMovement 游玩验收。

**退出条件：** 三个留存门框使用相同的新增诊断规格通过双端检查；全部堵门反例拒绝；
新增通行 gate 复用 R6 模块门框唯一一次回归的产物和已导入 UE 资产，执行一次双端验收，不另起三轮建模。
通行规格作为独立验收请求提前冻结；新合同的解析、冻结和兼容性由 R3 专项 probe 覆盖。
旧 18 个样本保留原合同和结果，补充检查以新报告引用，不覆盖历史。

## 7. R4：固定图评审的可重复校准

将视觉 rubric 在作者开始前与规格一起冻结，逐项引用原 requirement，定义 PASS/GAP 的可观察依据。
响应为每条判据记录证据视图与具体观察；看不清或缺少必要视角不能根据作者描述通过。
树根案例要求能从预登记视图辨认需求规定的三条根；不把“有三个网格”或“有三条骨架线”当成形状可读。
若原需求没有给出根数或尺寸，不凭校准目标添加艺术约束。
宿主固定相机、光照、色彩管理、背景及导出重导入流程；需要下部斜视角时在视图策略中预先声明。
对程序化材质必须评审实际导出图，而非只看 source。

离线固定 12 组证据：4 组明确正例、4 组明确负例、4 组边界例；包含根部融合、导出失色、缺部件和视角不足。
由人工/维护者预登记判据与标签，不使用待测 reviewer 自己的输出定义真值。
每组做 5 次独立评审，每次最多 3 次格式尝试，共 60 个评审槽位、最多 180 次调用；无效响应也入报告。
60 个槽位全部获得有效响应才算完成校准；耗尽槽位记失败，不能补抽到足够 PASS。
明确正负例的逐判据跨重复一致率目标 ≥90%，并要求 20 个明确负例槽位无误接受；报告分母及不确定项。
一致率定义为各证据组、各判据的最常见有效结论次数之和除以总有效判定数；另要求与预登记真值的一致率 ≥90%。
这里的最常见结论仅用于统计，不作为生产投票接受规则；缺失有效结果的槽位不能从完成率中剔除。
边界例单独报告分歧并改进判据/证据；修改策略后作为新版本评测，不能筛掉不利响应。
这只是小样本发布门槛，不将结果解释为总体错误率。

生产仍以首个有效评审为本轮结论，有效 GAP 进入资产修复；不以多数投票或反复评审把同一资产改判通过。
固定图重评是离线诊断流程，与生产重试政策隔离。

## 8. R5：降低作者接口试错与无效自检

在自有 `skills/yahaha-blender-modeling/` 增加经过本机验证的 helper 和简短示例，保留上游固定版本文件不变：

- Blender 5.2 动作创建/读取，使用当前 layered Action 接口；动作测量读取依赖图求值后的网格，而非原始顶点。
- World 为 null 时初始化；渲染选项通过可用枚举检查；安全序列化 Vector/IDProperty/数组和非有限数值。
- 导出可用材质：常量颜色/PBR 连接与必要烘焙；用重导入后的颜色/贴图证据检查程序化材质是否真的导出。
- 工作区内路径处理与 UTF-8 BOM 读取，测试中文和空格路径；不对整个脚本文本盲目删除字符。

在 skill plan 中增加相应 helperDirectories 并纳入哈希锁；新增脚本只落在 `skills/` 或 `worker/`。
作者提示明确本次截止时间、剩余时长、阶段产物及已知接口范例。
blockout 仅提交粗模、recipe 和 manifest；final 交付合同要求的导出及一次有界自检后返回，由宿主做正式验收。
先保留原作者次数/总预算；若还需调整阶段时间分配，另开单变量实验，不与接口修复混在同一收益统计中。
本轮 MCP 进程耗时占比较低且不包含所有宿主工作，不能据此推出完整性能瓶颈；暂不引入常驻 Blender 服务。

**退出条件：** 每个 helper 在 Blender 5.2.1 执行；能发现导出颜色缺失和无实际变形；
最小绑定模型端到端 probe 有成功 MCP 凭证、完整导出和宿主证据。预算耗尽及重启用例沿用 R0 验证。

## 9. R6：验证矩阵、对照口径与发布

### 9.1 从便宜且确定的检查开始

1. 每批执行 Node 语法检查、相关 worker 单元测试，以及 Python 语法检查；避免在源码树生成运行输出和缓存。
2. Windows Blender 执行正负 fixture、中文路径和进程停止 probe；R3 执行真实 UE 查询，不能只依赖 mock。
3. 新工具对 14 个已接受资产及相关失败留存资产只读重验，保留两套版本结果；已接受文件哈希不变。
4. 通过后按第 9.2 节启动分层样本：已达标类别各 1 次回归，未达标类别各 3 轮，共 12 个候选版任务。
   执行前冻结类别分组、清单、输入、模型配置、预算、并发方式和版本；留存资产只读重验不计为新的建模轮次。

计划测试文件包括 `worker/tests/modeling-execution.test.mjs`、`modeling-review.test.mjs`、
`modeling-traversal.test.mjs`（均新增），并扩展现有 `modeling.test.mjs`、`modeling-v2.test.mjs`、
`modeling-v2-gates.py`。验证外部行为、故障注入和预算不变量，不只断言实现里的常量。
每批记录实际命令、版本、通过/失败数及未执行原因；所有运行证据写入仓库外的新 audit 目录。

### 9.2 完整样本门槛

“已达标”以该类别的完整目标为准。改色任务虽然最终 3/3 PASS，但复用路线仅 2/3，仍归入未达标类别。
已达标的硬表面、参考图低模武器、模块门框各回归 1 次；复用、有机道具、简单绑定角色各保留 3 轮。
候选版总量为 `3 × 1 + 3 × 3 = 12`，不再要求六类全部重新运行三轮。

| 类别 | 历史结果 | 新轮数 | 新批次最低退出条件 |
| --- | --- | --- | --- |
| 精确尺寸硬表面 | 3/3 达标 | 1 | 1/1 DCC 全门槛及独立视觉通过 |
| 已有资产改色/局部修改 | 任务 3/3，复用仅 2/3 | 3 | 3/3 任务通过且实际走复用；源文件哈希不变；修改范围有几何/材质对比 |
| 参考图低模武器 | 3/3 达标 | 1 | 1/1 技术及参考要求通过，不弱化原参考约束 |
| 模块门框 | 3/3 DCC、UE 通过 | 1 | 1/1 技术、视觉、UE 通过；同一产物补充新增通行 gate，1/1 双端通过 |
| 有机静态道具 | 2/3 通过 | 3 | 3/3 导出材质、部件可读性通过；固定图校准另行达标 |
| 简单绑定角色 | 0/3 通过 | 3 | 3/3 完整作者凭证、导出材料/权重/实际动作、独立视觉通过；仅 DCC 能力，不标 UE skeletal ready |

任何样本失败都保留在预登记批次中。修复后另开版本/批次，不能替换失败样本拼成 12/12。
单次回归如失败，该类别验收不通过，先定位修复，再另记一次回归；不自动扩为三轮或连续补抽直到通过。
正确识别真实质量缺陷可以证明 gate 有效，但不等于该类别建模成功；两项分别报告。
六类能力全部达标才宣布本轮 P4 全范围通过。现有开关不是分类别开关，不能声称仅打开静态类别就自动屏蔽角色。

### 9.3 对照实验分开做

- **修复前后对照：** cf86fe4 与候选版使用同一原始完整规格、输入、作者模型/预算，并采用第 9.2 节相同配额，
  每版 12 个任务，合计 24 个任务；已达标类别每版只运行一次。
  固定并交错两版执行次序、保持同等并发资源；历史 18 个样本用于诊断，不能单独承担同期性能基线。
  同时保留各版本在线判定，并用同一最终检查器对两组输出做只读复验，分开比较资产质量与 gate 判定。
  第 9.2 节的候选版 12 个任务直接组成此对照的一半，事先统一登记配置与执行次序，不额外重跑候选版。
- **新增通行能力：** 使用独立冻结的通行规格和已知正负例，复用模块门框一次回归的产物及 UE 导入结果，
  不额外启动完整建模任务；旧 cf86fe4 不支持扩展字段，不能假称两版执行了相同新 gate。
- **旧流程对照：** 保留原 P4 要求，构建仅用于 probe 的适配入口，让旧作者流程接收同一完整规格，
  用共同的终态检查器验收。仅关闭 V2 或删除 contract 会改变题目，不是有效对照；缺失必需产物照常计 GAP。
  适配器不能额外替旧流程补做模型内容，其行为和代码版本要进入批次清单。
  旧流程同样采用第 9.2 节的 12 个任务配额，与已有候选版结果比较，不再次生成候选版样本。

报告逐项通过率、复用路线兑现率、真实质量修复数、无效评审次数、作者/评审调用数、总耗时中位数与范围、
已完成调用 usage、第三方额度及 fallback 原因。没有完整账单时不推算总费用。
各类别单独报告实际分母，不能将新的分层 12 样本总通过率直接与历史均衡 18 样本总通过率作提升比较。
仅一次的类别用于发现回归，报告单次耗时，不据此声称统计上的成功率或性能提升。
修复前后回归不能替代旧流程收益结论；旧流程同规格对照未完成时，P4 的比较性验收保持未完成。

### 9.4 部署与回滚

本机是 worker，代码仅改 `worker/`、`skills/`，文档在 `knowledgebase/`。按当前设计无需跨目录代码例外。
运行进程直接使用 `D:\game` 工作树，因此实际实施应在独立 Git worktree 完成，避免修改正在运行的工具文件。
测试输出、模型、执行日志、机器配置及 Tripo key 不进入 Git；新工作树通过已有外部配置使用凭据，不能复制后误提交。
启动仍检测 key 是否可用；缺失时跳过第三方路线。无额度、服务中断或结果不可用必须直接回退 Blender。

每批提交前检查 `git diff --cached --name-status` 和 `git diff --cached --check`，只暂存该批明确文件。
发布时先停止新分配，等待 worker 无活动 allocation、队列为空、execution journal 清空，再停止旧 agent/launcher。
保留 journal、provider ledger、任务工作区与产物；活动任务未完成时不能切工具版本。

准备一个指向审核通过 SHA 的干净命名分支/工作树，使用仓库 `worker/deploy/deploy-worker.ps1` 的
`-RepoRoot`、`-WorkerRoot` 参数部署，并核对 `runtime/deployment.json` 和启动后版本。
脚本目前没有 `-Commit` 参数；固定版本发布不使用会移动分支的 `-Update`。
`-CheckOnly` 同样要求旧 worker 已停止，不能在活动进程上当作无影响的部署预检。
部署后检查注册、V2 实际值、错误日志和隔离 smoke，记录精确 SHA；不能因仓库默认值为 0 而覆盖本机已启用配置。

出现误接受、预算重置、重复生成付费或停止未确认，立即停止新分配并保留证据。
任务排空后通过同一 Git 脚本回滚到上一个验证过的 SHA；显式 v2 活动合同不通过关闭开关降级。
回滚不删除新证据、不修改旧批次结果，也不使用 tar 或直接改已安装 release 代替 Git 部署。
